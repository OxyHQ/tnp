# TNP Phase 0 technical audit — 2026-08-06

Audit of `OxyHQ/tnp` at `96b8187` (branch `main`). Every claim below was verified by
reading the code or by running the command shown. Where a finding could not be
confirmed by observation it is labelled **unverified** and says so.

This document is a snapshot. It is not maintained as the code changes — it is the
baseline that the roadmap in [`roadmap.md`](./roadmap.md) is measured against.

### Cross-package coupling that must go

`apps/dns-server/src/index.ts` imports from `../../../packages/client/src/proxy`
— a relative path that reaches across a workspace boundary. `@tnp/dns-server`
does not declare `@tnp/client` as a dependency. This is why B1 was never caught.

## 3. Broken — does not work today

### B1. `apps/dns-server` does not typecheck and runs with an incomplete config

`apps/dns-server/src/index.ts` builds a `TnpConfig` literal with 5 fields.
`TnpConfig` (`packages/client/src/config.ts`) declares 18 required fields. The
13 missing ones include `privacyLevel`, `socksPort`, `identityKeyPath` and
`publicDnsIp`. Bun strips types at runtime, so the process starts and the fields
are `undefined`. Nothing catches this because the package has no typecheck script
and no CI gate runs one.

### B2. `tnp relay` can never register

Two client/server contract mismatches, both fatal:

| Client call | Sends | `apps/api` expects |
|---|---|---|
| `TnpApiClient.registerRelay` (`api.ts:171`) | `{ port, location }` | `{ endpoint, publicKey, operator, capacity: { maxConnections, bandwidth } }` |
| `TnpApiClient.sendRelayHeartbeat` (`api.ts:196`) | `{ relayId, serviceNodes, activeCircuits }` | `{ endpoint }` |

`POST /relays/register` returns 400 (`endpoint is required`) for every call the
client makes. `relay-node.ts:179` wraps that in `throw new Error("Failed to
register relay: …")`, so relay mode aborts at startup whenever an auth token is
configured. Community relays are therefore not merely undocumented — they are
unreachable.

### B3. Upstream DNS answers are re-encoded incorrectly

`DnsProxy.forwardUpstreamRaw` (`proxy.ts:224`) fetches JSON from a hardcoded DoH
endpoint and hand-builds a wire response. Confirmed defects:

- **The response code is hardcoded to `0x8180`** (NOERROR). An upstream NXDOMAIN
  is re-encoded as NOERROR with zero answers. A client cannot distinguish "does
  not exist" from "exists with no records of this type", so negative caching and
  `curl`'s error reporting both go wrong. Issue #7 asks precisely for this
  ("Resolver failures fail safely and do not silently return incorrect empty
  responses") — today they do not.
- **RDATA for every type other than A, AAAA and CNAME is written as a raw UTF-8
  blob.** TXT requires length-prefixed character-strings; MX requires a 16-bit
  preference followed by a domain name; NS/SRV/CAA each have their own encoding.
  All are wrong on the wire.
- **No name compression**, no AUTHORITY section, no ADDITIONAL section, no
  EDNS(0) (so no responses over 512 bytes), no TC bit, so a truncated answer is
  silently short rather than signalling retry-over-TCP.
- `writeResponse`'s fallback path (`proxy.ts:415`) writes `RDLENGTH = 0` for
  every record that is not an A record, emitting structurally valid but empty
  answers for TNP-native CNAME/TXT/MX/NS records.

### B4. The `upstreamDns` setting does nothing

`TnpConfig.upstreamDns` defaults to `1.1.1.1` and is surfaced in the interactive
settings editor. `DnsProxy` never reads it. All public queries go to
`https://8.8.8.8/resolve` (Google's DoH JSON API), hardcoded at `proxy.ts:233`.
Every TNP user's public DNS traffic is sent to Google regardless of what they
configure — a privacy property that is neither documented nor selectable.

### B5. `--privacy private` is accepted and does nothing

`cmdConnect` (`cli.ts:108`) parses `--privacy private`, stores it, and prints
`privacy: private`. There is no multi-hop code anywhere in the repository —
`grep -ri 'onion\|guard\|layered'` over `packages/client/src`,
`apps/relay/src` and `packages/protocol/src` returns nothing. A user who selects
the private level gets exactly the single-hop path, with a status line telling
them otherwise. This is the most serious honesty defect in the codebase and is
fixed in Phase 1 by rejecting the flag until Phase 6 lands.

## 4. Security findings

Severity is judged against the product TNP claims to be, not against a demo.

### S1 — CRITICAL — Circuit IDs are one global, client-chosen namespace

`apps/relay/src/connections.ts` keeps `circuits` as a single
`Map<number, Circuit>` keyed only by the client-supplied `circuitId`.
`handleClientMessage` (`index.ts:177`) looks up `manager.getCircuit(frame.circuitId)`
with no check that the requesting socket owns that circuit.

Consequences, all reachable by any client that can open a WebSocket to `/tunnel`:

- Send `DATA` on another client's circuit ID and the relay forwards the frame to
  that circuit's service node. The payload will fail the victim's Poly1305 check,
  but the service node's error path (`service-node.ts:299`) emits an `ERROR`
  frame that the relay forwards to the **victim**, which is a remote-triggered
  teardown of someone else's connection.
- Send `CLOSE` with a guessed ID and `manager.closeCircuit` deletes the victim's
  circuit unconditionally.
- `openCircuit` (`connections.ts:80`) closes an existing circuit with the same ID
  and replaces it, so an attacker can steal the ID outright.

Guessing is not required: `TunnelManager.nextCircuitId` (`tunnel.ts:129`) starts
at `1` in every client process, so two honest clients on one relay collide on
circuit 1 immediately. Concurrency is broken before any attacker appears.
The same defect is duplicated in the embedded relay
(`packages/client/src/relay-node.ts`).

**Fix direction:** circuit IDs must be scoped per connection and namespaced by
the owning socket, and must be generated from a CSPRNG. Both are Phase 3.

### S2 — CRITICAL — Anyone can claim any domain on a relay

`apps/relay/src/index.ts:45` upgrades `/service?domain=<anything>` with no
authentication whatsoever, and `ConnectionManager.registerServiceNode`
(`connections.ts:35`) **replaces** an existing registration for that domain and
tears down its circuits. An attacker connects to a relay with
`?domain=victim.ox` and from that moment the relay routes every circuit for
`victim.ox` to the attacker.

End-to-end encryption does not save the victim's users here: the client derives
its shared key from a public key it fetched from the API, so an attacker who
holds the routing position but not the key simply causes total denial of service
— and combined with S3, can do worse.

The embedded relay in `packages/client/src/relay-node.ts` has the same hole.

### S3 — CRITICAL — The end-to-end key is trust-on-API, with no signature chain

The service node generates a fresh X25519 keypair at every start
(`service-node.ts:66`), `POST`s the public half to the API, and the API hands it
to any client that resolves the name (`routes/dns.ts:93`). The client
(`tunnel.ts:152`) derives the session key from that value and never verifies
anything about it.

Nothing binds the key to the domain, to the domain's owner, or to an Oxy
identity, and nothing is signed. The API is a fully trusted, unaudited
man-in-the-middle: substituting one field in one JSON response transparently
decrypts and re-encrypts all traffic for that name with no client-visible signal.
`docs/index.mdx` nonetheless describes the tunnel as "end-to-end encrypted",
which is true only against the relay, never against the API.

Compounding this: `loadOrCreateIdentity` generates an **Ed25519 identity keypair
and the code never uses it**. `identity.publicKey` is printed to the console and
then dropped. There are no signatures anywhere in the protocol.

### S4 — HIGH — Public DNS names are shadowed by default

Three independent places make this the shipped default, not an opt-in:

1. `apps/api/src/seed.ts` seeds `.com` and `.app` as TNP TLDs on a fresh database.
2. `packages/client/src/service.ts:63` (`installDarwin`) writes
   `/etc/resolver/ox`, `/etc/resolver/app` **and `/etc/resolver/com`**, pointing
   every `.com` lookup on that Mac at the TNP resolver.
3. `installLinux` (`service.ts:100`) writes a systemd-resolved drop-in with
   `Domains=~.`, which makes TNP the routing domain for **all** DNS.

The mitigation in `DnsProxy.handleQuery` — skip the TNP API for non-custom TLDs
unless there is a positive cache entry — reduces API traffic but does not change
the outcome: once a `.com` name is registered in the TNP registry, it resolves
differently for TNP users than for everyone else, silently. This is the exact
scenario issue #6 forbids. Policy and migration: [`naming.md`](./naming.md).

### S5 — HIGH — No authentication, replay, downgrade or rotation protection in the transport

There is no protocol version byte, no capability negotiation, no handshake, no
signature, no message counter and no replay window. `encrypt()` uses a random
24-byte XSalsa20 nonce, which is large enough that random collisions are not the
concern; the concern is that a relay can **replay** any recorded `DATA` frame and
the receiver will accept it as fresh, and that neither side can detect a peer
being swapped mid-connection.

### S6 — HIGH — Unbounded frames, unbounded queues, no backpressure

`decodeFrame` enforces a 5-byte minimum and no maximum. Neither relay checks
message size before buffering. Neither the SOCKS5 pump (`socks.ts:212`) nor the
service-node pump (`service-node.ts:263`) ever pauses its socket or inspects
`bufferedAmount`, so a fast producer and a slow consumer grow the WebSocket send
buffer without limit. `DnsProxy.cache` is a `Map` with no size cap and no
eviction. Every one of these is a single-client memory-exhaustion path against a
shared relay.

### S7 — MEDIUM — Reflected HTML injection in the parking page

`apps/api/src/index.ts:99` interpolates `req.hostname` into the parking page's
`<title>`, `<h1>` and a link `href` with no escaping. Verified against Express
5.2.1 (the version in `bun.lock`): `req.hostname` returns the raw `Host` header
value, and `Host: a.ox<script>alert(1)</script>` is reflected verbatim into the
response body. The parking branch is reached whenever the last label matches an
active TNP TLD, which a crafted host satisfies.

Honest severity caveat: a browser will not let page JavaScript set the `Host`
header, so this is not directly exploitable from a hostile web page. It is
reachable by anything that controls the request path to the API — a proxy, a
misconfigured CDN, or a client tricked into using an attacker's resolver — and it
is an unescaped reflection in a production HTML response either way. Escape it.

### S8 — MEDIUM — No DNSSEC, no resolver choice, no leak protection

Public answers come from one hardcoded DoH endpoint (B4) with no DNSSEC
validation, no configurable upstream, no DoT, and no classic DNS path. When the
SOCKS5 proxy is running there is no mechanism that prevents an application from
resolving a name through the system resolver before connecting — remote
resolution exists in the SOCKS5 address parser but nothing enforces its use.

### S9 — MEDIUM — DNS caching ignores record TTLs and never caches negatives

`resolveTnp` stores every entry with `config.cacheTtlSeconds` (default 300)
regardless of the TTL the record actually carries, and stores nothing on a
negative answer, so every lookup of a nonexistent name is a fresh round trip to
the API.

### S10 — MEDIUM — The kill switch has no ownership or integrity model

The kill switch writes firewall rules and records a PID in
`${tmpdir()}/tnp-killswitch-active` with mode `0600`. On a multi-user Linux host
`/tmp` is world-writable; the marker's presence is what a later `tnp connect`
uses to decide whether stale rules need clearing. The failure mode is a
recoverable one (rules cleared or not cleared), not privilege escalation, but the
marker belongs in the data directory, not `/tmp`.

| Claim | Where | Reality |

| "TNP is DNS-only. It does not route traffic, does not act as a VPN" | `README.md:5`, `docs/index.mdx:15` | The client ships a SOCKS5 proxy, an encrypted overlay transport, a service-node mode and an embedded relay. It routes traffic. |
| "Client: Go DNS resolver daemon (scaffold)" | `README.md` tech stack | The client is TypeScript compiled with `bun build --compile`. There is no Go. |

The README understates the product in one direction (calling a traffic-routing
client "DNS-only") and the release notes overstate it in the other (calling a
trust-on-API tunnel "end-to-end"). Both are corrected in this PR.

## 6. Reusable vs. replaceable

**Keep and build on:**

- `apps/api` registry model and the Oxy auth wiring (`requireOxyAuth`,
  `getRequiredOxyUserId`) — ownership checks on domains, nodes and relays are
  present and correct.
- `apps/web` — the dashboard is the right long-term shape for the control plane.
- `packages/client/src/crypto.ts` — correct use of correct primitives; it needs a
  key hierarchy around it, not a rewrite.
- The service-node outbound-connection model (no inbound ports, exponential
  backoff reconnect) — the architecture is right, the authentication is missing.
- The installer scripts and OS service integration — real work, needs the
  namespace policy applied to which TLDs it captures.
- `packages/protocol` frame codec — the right layering; it needs a version,
  bounds and structured errors.

**Replace:**

- `DnsProxy`'s hand-rolled wire serialization (B3) — replace with a maintained,
  standards-compliant DNS layer.
- The relay's circuit table (S1) and its unauthenticated upgrade path (S2).
- The trust-on-API key distribution (S3) — replace with a signed record chained
  to the domain owner's Oxy identity.
- `apps/dns-server`'s relative-path import of the client (B1) — replace with a
  real `@tnp/resolver` package both consume.
- `packages/client/src/socks.ts` — CONNECT-only, no IPv6, no auth, ignores the
  requested port, cannot reach the public internet, and discards pipelined bytes
  after the greeting (`socks.ts:94`). Rewrite against RFC 1928.

**Delete:**

- The unused Ed25519 identity plumbing, once a real key hierarchy replaces it.
- `TnpConfig.upstreamDns` or its hardcoded bypass — one of the two must go.

## 7. What is out of scope

Per the current product direction, the following are **not** to be implemented
and no interfaces, adapters or mocks for them may be added: OpenProvider, ICANN
reseller integration, traditional domain sale/transfer/renewal, the reseller
system, FairCoin payments, checkout and billing, and ICANN registrar
accreditation.

A grep for `openprovider|faircoin|checkout|stripe|reseller` over all TypeScript,
TSX, JSON and Markdown outside `node_modules` and `dist` returns **no code
matches** — only the word "ICANN" in marketing copy in the i18n bundles. The
codebase is clean of these today and must stay that way. Issues #12 and #14
should be closed as out of scope.
